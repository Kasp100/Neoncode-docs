# Regular Types, Copyable, and Serialisable

Neoncode is object oriented: **classes**, **abstract classes**, and **interfaces** are used to define **types**.

Neoncode has a few built-in contracts for **types** that ensure:
- Serialisability: `serialisable`, and
- Copyability: `copyable`

Serialisable automatically also means copyable, but copyable does not necessarily mean serialisable.

## 1. Default

Types that are not marked `serialisable` or `copyable` are non-serialisable and non-copyable.

To instantiate these types, the programmer needs a constructor that initialises all uninitialised fields.

## 2. Serialisable

**Syntax**: keyword `serialisable` after type name in declaration

Instances of a serialisable type can be transferred to the outside and back. E.g., writing an object to a file and reading it back later.

Serialisable types do not need an explicit constructor. The compiler provides a constructor for free based on the type's fields.

### Contract

- All field must also be serialisable. All primitives are serialisable types.
- Cannot have `shared` fields.
- Instances can be freely copied using `copy`.
- Instead of fields being fully private (which is the case for normal types), fields can be **read** (from the outside) using `serialising` blocks.


### Example

```
pkg main;

import std::format_convertors;

public class s_uuid_v4 serialisable
{
	uint32 a;
	uint16 b;
	uint16 c;
	uint16 d;
	uint48 e;
}

public pure_function_set serialising_example
{
	public string stringify(s_uuid_v4 uuid)
	{
		mut:string_builder sb = ();

		serialising uuid
		{
			sb.append(format_convertors::number_to_hex_string(uuid.a)); // `uuid.a` wouldn't be allowed outside the `serialising` block.
			sb.append('-');
			sb.append(format_convertors::number_to_hex_string(uuid.b));
			sb.append('-');
			sb.append(format_convertors::number_to_hex_string(uuid.c));
			sb.append('-');
			sb.append(format_convertors::number_to_hex_string(uuid.d));
			sb.append('-');
			sb.append(format_convertors::number_to_hex_string(uuid.e));
		}

		ret sb.build();
	}
}
```

### Guidelines

- **The contents of serialisables cannot be trusted.**
- Serialising and deserialising code is preferably generated by **[compile functions](./compile_functions.md)**
	- Compile functions can generate a serialisation and deserialisation code according to the fields of the serialisable type.
	- This avoids runtime reflections, which means less performance overhead.
	- Compile functions are made for a specific serialisation format (e.g. XML, binary, etc.).
	- This is safe, given that the compile function properly escapes user data and ensures integrity.

## 3. Copyable

**Syntax**: keyword `copyable` after type name in declaration

Copyable types allow their instances to be duplicated using the `copy` keyword.  
In copyables:
- Every field must either be `shared` or have a copyable type.
- `shared` fields retain their reference during copying.
- All other fields are deeply copied.

> If custom copying behavior is required, you cannot use these keywords and must implement copying manually.
